# LDE v0.7 Multi-Distro Portability Evidence Summary

## 1. Executive Summary

This document provides the minimal durable, sanitized evidence summary for the Linux Diagnostic Engine (LDE) v0.7 cross-distribution portability validation, closing the portability validation requirements established in TASK-LDE-07 and TASK-LDE-07B.

Validation was conducted against clean, official virtual machine environments running real Fedora and Debian operating systems with UEFI firmware and mounted EFI System Partitions (ESP). Source code equivalence between the development working-tree and the guest execution environments was verified via cryptographic SHA-256 hashes.

## 3. Package and Kernel Normalization Results

### Fedora 44 (RPM Ecosystem)
- **Package Inventory:** Queried via machine-readable `rpm -qa --qf '%{NAME}|%{VERSION}|%{RELEASE}|%{ARCH}\n'`.
- **Kernel Deduplication:** Split RPM packages (`kernel`, `kernel-core`, `kernel-modules`, `kernel-modules-core`) were properly parsed and deduplicated to the single installed kernel release matching the running kernel.
- **Foreign / Orphan Policy:** DNF repository-dependent foreign and orphan package classifications were left unconfigured rather than emitting false positives.

### Debian 13 (dpkg Ecosystem)
- **Package Inventory:** Queried via machine-readable `dpkg-query -W -f='${db:Status-Abbrev}|${Package}|${Version}|${Architecture}\n'`.
- **Status Filtering:** Only packages with status `install ok installed` (`ii`) were enumerated, cleanly separating installed `linux-image-*` packages from uninstalled or purged package records.
- **Meta-package Distinction:** Real versioned kernel packages were distinguished from metapackages (`linux-image-amd64`).

## 5. LDE Engine Runtime and Sanitization Results

- **Command Execution:** `python3 syscheck.py --capabilities`, `python3 syscheck.py --format json`, and `python3 syscheck.py --format markdown` all executed cleanly with exit code 0 on both platforms.
- **Source Capabilities:**
  - Fedora: System journal, kernel journal, systemd system, NetworkManager, and Btrfs sources were identified as available; uninstalled tools (upower, nvme, pci, usb, sensors) were cleanly categorized as `UNAVAILABLE`.
  - Debian: System journal, kernel journal, systemd system, and PCI sources were identified as available; uninstalled tools (btrfs, upower, nvme, usb, sensors) were categorized as `UNAVAILABLE`.
- **Sanitized Snapshot Findings:**
  - Fedora: 0 findings emitted. Clean baseline verification.
  - Debian: 1 finding emitted: `KERNEL-FIRMWARE-LOAD-FAIL-001` (severity P2). The finding was corroborated by kernel journal entries confirming failure to load wireless regulatory database firmware (`regulatory.db`).
- **Data Sanitization Verification:**
  - Hostnames, machine IDs, hardware identifiers, and IP addresses were sanitized to generic placeholders (e.g., `<HOST>`).
  - No unredacted machine identity leaks were found in sanitized reports or snapshots.

## 9. Explicit Evidence Limitations and Scope Boundary

1. **Systemd Runtime State:** Systemd manager reported `starting` (exit code 1) during guest cloud-init execution; no fully settled `running` state is claimed.
2. **Signature Verification:** Image checksums were verified against HTTPS download sources; detached GPG signatures were not validated.
3. **Hardware Scope:** Virtual machine execution validates software portability across distribution package managers, init systems, and filesystem layouts. It does not certify physical discrete GPU hardware behavior (AMD, Intel, NVIDIA).
4. **UKI Architecture:** Neither cloud distribution image employed a Unified Kernel Image (UKI). UKI status is formally documented as `NOT_OBSERVED`.
5. **Product Version String:** Working-tree code continues to report product version `0.6.1`. Source code equivalence was established strictly by SHA-256 checksums rather than version text.
