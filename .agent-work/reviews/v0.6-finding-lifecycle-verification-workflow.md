## 4. Lifecycle identity contract

- `NEW`: current `finding_id` is absent from baseline.
- `PERSISTENT`: the same `finding_id` exists in both snapshots.
- `RESOLVED`: baseline `finding_id` is absent from current and its required
  baseline source lineage passes the authority guard.
- IDs are sorted lexically in all lifecycle result collections.
- Duplicate or empty Finding IDs are rejected for lifecycle comparison; loaded
  duplicate snapshots fail through existing snapshot validation.
- Historical snapshots are immutable. The comparator creates new result data
  and does not mutate either input snapshot.
- Evidence, recommendation, interpretation, severity/confidence, and volatile
  timestamps do not create a new lifecycle identity.

## 5. Source-authority / resolution contract

- A baseline Finding must have persisted Observation/RAW lineage. Missing or
  incomplete lineage is `Unverified`, not `Resolved`.
- Relevant current restrictions containing existing non-authoritative markers
  such as failed, timeout, permission, malformed, truncated, unavailable, or
  unknown block resolution. Unrelated source restrictions do not block an
  otherwise authoritative source.
- Current matching RAW provenance/payload with failed execution, truncation, or
  explicit `authoritative: false` also blocks resolution. Matching incomplete
  or contradictory current observations block resolution.
- Stable `source_query` metadata was added to existing RAW payloads where older
  Finding families lacked it. Known Finding-ID query fallbacks keep v0.5 schema
  3 snapshots usable without inventing a new schema field.
- `Unverified` is a verification result for unresolved proof, not a fourth
  Finding lifecycle state. It is emitted only when needed.
- The policy uses the existing collector contract: a successful no-hit source
  has no relevant non-authoritative restriction. A future explicit positive
  source-coverage record would reduce reliance on that existing negative
  limitation contract, but is not required for the current schema-3 slice.

## 6. CLI verify behavior

- `snapshot create --output PATH` runs the existing read-only pipeline and
  creates a collision-safe schema-3 baseline.
- `verify BASELINE` validates baseline schema and compatibility before running
  the current pipeline, then prints compact English sections for `Resolved`,
  `Persistent`, and `New`; `Unverified` appears only when non-empty.
- `verify --json BASELINE` uses the established JSON convention and exposes
  baseline/current identities, all lifecycle ID sets, and relevant source
  limitations.
- Verification does not print the generated Markdown report. The reused
  runtime pipeline still writes its normal current report to the selected
  report directory, as existing `run` does; no system state is changed.
- Errors for missing, malformed, incompatible, duplicate, or colliding inputs
  are controlled CLI errors without tracebacks.
- Human verification output contains no ANSI escape sequences; `NO_COLOR` is
  respected and has no effect on the already deterministic non-TTY output.
